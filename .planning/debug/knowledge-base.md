## balloon-no-data-oled-blank — balloon never transmitted + dark OLED; script-less web page behind it
- **Date:** 2026-08-23
- **Error patterns:** no telemetry received, OLED completely dark, page loads but data never updates, no /api/state polls, silent macro redefinition, String append silently dropped, boot aborts at sensor manager
- **Root cause(s):** (1) BMP280_ADDRESS macro collision — sensor_pins.h 0x76 vs Adafruit_BMP280.h (0x77), library value silently wins at the call site (angle-bracket include suppresses the redefinition warning), so the probe hit 0x77 while the sensor ACKs at 0x76; (2) SensorManager::begin made an optional-sensor init failure fatal, converting the wrong address into total loss of beacon + OLED; (3) handleRoot built the ~80 KB dashboard as one Arduino String — operator+= silently drops the append when the realloc cannot find a contiguous block on the fragmented station heap, shipping the page without its 57 KB footer script (23,027 of 80,467 bytes, byte-exact)
- **Fix:** rename macro to BMP280_I2C_ADDRESS + probe both legal strappings with explicit literals; degrade (not abort) on absent BMP; stream the page in 3 parts from PROGMEM (setContentLength + sendContent); UART0 bring-up diagnostics on both boards
- **Files changed:** include/sensor_pins.h, src/sensor_manager.cpp, src/main_balloon.cpp, src/status_display.cpp, src/main_basestation.cpp, src/command_sender.cpp, src/image_rx_manager.cpp
- **Why not caught:** no gate existed for this class — phase 01/02 verification was code-level only (RF round trip was permanently PRESENT_BEHAVIOR_UNVERIFIED pending hardware UAT, and the UAT was blocked by cause 1, hiding causes 2 and 3); the web UI's script delivery was never asserted by any test (a page-loading check with a script-execution oracle would have caught it on day one); the silent-failure modes (macro redefinition via system headers, String operator+= OOM drop) produce no build or runtime error of their own
- **Recurrence guard:** BMP280_I2C_ADDRESS rename with collision-explaining comment (config-default change); UART0 diagnostic traces make every boot/serve path self-evidencing on the bench ([BMP]/[BCN]/[PAGE]/[API]/[NET] — new de-facto regression observatory); graceful-degrade pattern documented for all optional sensors; page-streaming pattern (never build large responses as one String) now exists in-repo beside handleLeafletJs for future handlers to copy
- **Prevention (blameless postmortem):** Why did the balloon send nothing? The I2C address macro resolved to the wrong value. Why silently? Two headers define the same macro name; the library one wins and the angle-bracket include path suppresses GCC's redefinition warning. Why did that kill the OLED too? Boot order made the sensor gate precede StatusOLED().begin, and the abort design made an optional sensor fatal — the diagnostics were downstream of the thing they should have diagnosed. Why did the web page stay empty after the link came up? A third, independent latent fault (footer-script truncation) was masked by the first two — every layer had been failing for its own reason since phase 03 grew the page past the heap's contiguous-block limit. Why wasn't any of it caught earlier? Because hardware UAT never got a clean shot: the balloon fault blocked link tests, which blocked web telemetry tests, and each phase's "works" verdict was code-level only. Guard: keep the UART0 trace set in every bench build, and add a hardware-UAT step that asserts script execution (tiles fill) — not just page load — before any web phase is declared verified.

## balloon-bootloops-at-bench — GPS UART1 RX mapped onto reserved OPI-PSRAM line GPIO35 → silent TG1WDT bootloop
- **Date:** 2026-08-27
- **Error patterns:** rst:0x8 (TG1WDT_SYS_RST) bootloop, 40+ consecutive resets at power-on, silent interrupt-watchdog wedge with no panic/backtrace output, hang inside Adafruit_SSD1306::begin or post-camera-init Wire burst, ESP_ERR_INVALID_STATE i2c storm when OLED unplugged, no GPS communication detected / GPS RX never sees a byte, works-on-test-firmware-but-bootloops-in-product, firmware-provenance false premise (same source assumed from source tree, refuted by build banner)
- **Root cause(s):** commit 02142e1 set GPS_TX_PIN (UART1 RX pad) = GPIO 35 — GPIO 35-37 are reserved octal-PSRAM (OPI) data lines on this board (platformio.ini: qio_opi / 16MB / psram_type = opi, N16R8-class) and must not carry any peripheral; claiming pad 35 via the GPIO matrix broke PSRAM accesses for the product app → silent interrupt-watchdog starvation → TG1WDT_SYS_RST bootloop with the hang site modulated by wherever the next PSRAM-touching window sat (39/40 inside SSD1306::begin, 1/40 post-camera-init). The config had been copied from src/test_lora_balloon.cpp, which "proves" GPIO 35 works only because the test app never exercises PSRAM (no camera); the GPS pin change and the bench re-wire landed between the same two sessions, manufacturing a false "hardware regression" verdict that survived three discriminator rounds until build-banner timestamps refuted the "same source as session 5" premise.
- **Fix:** permanent GPS_TX_PIN=41 in include/sensor_pins.h (free pin, not strapping, outside the reserved set) with the 45→35→41 history documented at the macro; GPS TX wire re-terminated to GPIO41 at bench; bench-verified (balloon11.log: hours of clean telemetry, zero resets; user-confirmed GPS data flowing on 41) — commit 3f2c2c6
- **Files changed:** include/sensor_pins.h, src/test_lora_balloon.cpp
- **Why not caught:** no gate existed for this class — the pin map's own validation list encoded per-peripheral assignments but not board-variant reservations (it listed 35 as a legal sensor pin and claimed "No conflicts detected"), no pin-reservation check and no hardware-in-the-loop boot test exist in this embedded project, and "proven on test firmware" was transferred into product config without noting the test app does not exercise the conflicted subsystem (PSRAM); additionally, firmware provenance was initially established from source-tree identity instead of build banners, which let the false premise stand through three builds
- **Recurrence guard:** forbidden-pin documentation in include/sensor_pins.h ("Never assign ANY peripheral to GPIO 35/36/37 on this board" — GPS block + Pin Validation list both name the OPI-PSRAM reservation and the prior stale-list failure); comment-only provenance guard at src/test_lora_balloon.cpp:42 (GPIO 35 "works" in the test app only because it never exercises PSRAM — do NOT copy into product); this KB pattern. Candidate future gate: bench boot-log assertion (zero rst:0x8 lines + "GPS communication detected" banner) on every flash
- **Prevention (blameless postmortem):** Why did the balloon bootloop at the bench? UART1 RX was routed onto GPIO 35, a reserved octal-PSRAM data line, and PSRAM accesses broke until the interrupt watchdog starved. Why was that pin chosen? A standalone test app had "proven" GPIO 35 during an earlier pin hunt (the 45→35 move chasing GPS data) and its config was copied into the product pin map — but the test app never touches PSRAM (no camera), so the conflicted subsystem was never exercised where the pin was proven: "proven on test firmware" is not transferable when the test app doesn't exercise the conflicted subsystem. Why did the pin map permit it? Its validation list tracked per-peripheral assignments, not board-variant reservations (OPI-PSRAM boards reserve GPIO 35-37), so it reported "No conflicts detected" — pin-map comments must encode board-variant reservations, not just ownership. Why did diagnosis initially blame hardware? The pin change and the bench re-wire landed between the same two sessions, perfectly confounded, and "same source as session 5" was believed on source-tree identity for three discriminator builds — until build-banner timestamps showed the passing binary predated the pin change: establish firmware provenance from build banners, never from the source tree. Why wasn't it caught at a gate? No hardware-in-the-loop boot test and no pin-reservation check exist (embedded, no test suite). Guard: the sensor_pins.h forbidden-pin block + the test-app provenance comment + this KB entry; future hardening candidate is a boot-log gate on every bench flash (zero rst:0x8 + GPS-bytes banner).
