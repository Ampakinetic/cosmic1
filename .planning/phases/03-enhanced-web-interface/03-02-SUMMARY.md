# Phase 3 Plan 2: Trajectory Map with Offline Fallback Summary

**Full-flight GPS track in a 500-point ring buffer, rendered on a firmware-served Leaflet map with altitude-banded polylines, auto-follow/Recenter, and a D-37 offline canvas fallback fed by the identical data**

## Performance

- **Duration:** 25 min
- **Started:** 2026-08-19T15:58:26Z
- **Completed:** 2026-08-19T16:23:08Z
- **Tasks:** 2
- **Files modified:** 10 (2 created src, 1 generated header, 1 script, 4 vendor, 2 modified)

## Accomplishments
- TrajectoryBuffer records one point per valid-GPS 0x14 beacon (seq-deduped, wraparound-safe, ~6 KB internal RAM); /api/state carries chronological `traj` array + `trajCount` — measured 14,009 B at the 500-point cap, under the 16 KB budget, so TRAJ_MAX_POINTS stays 500
- Leaflet 1.9.4 embedded as gzipped PROGMEM (JS 147,552→42,494 B, CSS 14,806→3,524 B) served from /leaflet.js and /leaflet.css with Content-Encoding: gzip and 24 h cache — the page never references a CDN, so it fully loads in AP mode
- Map section renders the altitude-banded track (#22c55e / #eab308 / #ef4444), a #22c55e circleMarker current position (no image assets), auto-follow that drag/zoom cancels with a Recenter chip, and the required OpenStreetMap contributors attribution
- D-37 offline fallback: tile failure (tileerror with zero successful tiles, or 8 s first-load timeout) swaps to an auto-scaled canvas plot of the identical traj array with the offline chip; tile recovery swaps back automatically; before the first valid fix only the waiting message renders

## Decisions Made
- Pull-based recording (Trajectory polls getTelemetrySnapshot) — zero changes to image_rx_manager
- Offline swap covers the Leaflet container with an opaque canvas instead of display:none, keeping tile events live for automatic recovery; every 3rd poll nudges a covered setView to re-request tiles
- tileerror falls back only while zero tiles have loaded; transient loss on a live map keeps the tiled view (8 s zero-tile timeout backstop)
- Single-point first fit: setView zoom 16 (fitBounds on zero-size bounds pins maxZoom)
- 1-point track renders marker only (no polyline); track rebuilds only when trajCount changes, marker updates every poll (D-36 diff discipline)

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Trajectory-aware json.reserve in handleApiState**
- **Found during:** Task 1 (traj serialization)
- **Issue:** The plan's fixed 4096-byte reserve (sized for the pre-traj payload) would force repeated heap reallocations as the traj array grows to ~13.4 KB at 500 points — avoidable fragmentation on a long-running loop (Pitfall 4)
- **Fix:** Reserve scales with live point count: `2048 + getCount()*28` bytes
- **Files modified:** src/main_basestation.cpp
- **Verification:** pio build SUCCESS; measured full-track payload 14,009 B < reserve at cap
- **Committed in:** aa1f8cf (part of task commit)
